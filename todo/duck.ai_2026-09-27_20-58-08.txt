Yes—but the clean hack is probably **not to resize windows yourself**. In Niri, tiled windows should expand and contract automatically if Noctalia changes its layer-shell **exclusive zone**—the reserved strut that tells the compositor how much screen space the bar occupies.

Noctalia currently has the two relevant controls:

```toml
[bar.main]
auto_hide = true
reserve_space = true
```

With `reserve_space = true`, the bar keeps reserving space even while hidden. With `reserve_space = false`, it retracts the bar as an overlay, but windows can overlap it when visible. The desired behavior is effectively a third mode: **reserve space only while the bar is visible**. That is already being proposed as a “smart” reserve-space mode. [1,2]

## Best solution: patch Noctalia’s exclusive-zone logic

The ideal change is conceptually:

```qml
function shouldReserveExclusiveZone(instance) {
    return instance.barConfig.reserveSpace &&
           (!instance.barConfig.smartReserveSpace ||
            instance.smartAutoHidePinnedVisible)
}
```

Then make sure `syncBarExclusiveZone()` is called whenever the bar’s visibility changes:

```qml
function reevaluateBarVisibility(instance) {
    // existing auto-hide logic...
    instance.smartAutoHidePinnedVisible = visible

    syncBarExclusiveZone(instance)
}
```

The behavior would be:

```text
bar visible   -> exclusive zone = bar thickness
bar hidden    -> exclusive zone = 0
```

Niri will then relayout its tiled windows in response to the changing exclusive zone. This is preferable to moving individual windows because it preserves Niri’s normal column and tile behavior.

The relevant Noctalia code path appears to be `shouldReserveExclusiveZone()` plus `syncBarExclusiveZone()`. The proposed implementation specifically notes that the visibility state is already reevaluated and that the exclusive zone is the only part that needs changing. [1]

## Practical workaround without patching

If you do not want to maintain a Noctalia fork, you can approximate it with two commands:

1. Hide/show the bar.
2. Toggle its reserved space at the same time.

For example, bind a script in Niri:

```bash
#!/bin/sh

# Adjust the bar name if yours is not "main".
noctalia msg bar-toggle main
sleep 0.05
noctalia msg bar-reserve-toggle main
```

Then in Niri:

```kdl
binds {
    Mod+B {
        spawn-sh "noctalia-smart-bar-toggle";
    }
}
```

However, this workaround has important problems:

- `bar-reserve-toggle` is a toggle, not an explicit set operation.
- The script can lose synchronization with the real bar state.
- Auto-hide may trigger independently and undo the expected state.
- A configuration reload can restore the configured `reserve_space` value.
- The delay may need tuning because bar visibility and exclusive-zone updates are asynchronous.

Those limitations are also documented in the current feature discussion. [1]

## A more robust external script

If you want to experiment anyway, keep your own state file instead of guessing:

```bash
#!/bin/sh

state="${XDG_RUNTIME_DIR:-/tmp}/noctalia-bar-state"

if [ -f "$state" ] && [ "$(cat "$state")" = "visible" ]; then
    noctalia msg bar-toggle main
    noctalia msg bar-reserve-toggle main
    printf '%s\n' hidden > "$state"
else
    noctalia msg bar-toggle main
    noctalia msg bar-reserve-toggle main
    printf '%s\n' visible > "$state"
fi
```

This is only reliable if the bar is controlled exclusively through that script. Mouse-triggered auto-hide, workspace changes, and Noctalia reloads can still desynchronize it.

## What I would implement

For a local fork, I would add:

```toml
smart_reserve_space = true
```

and use logic equivalent to:

```qml
return reserveSpace &&
       (!smartReserveSpace || smartAutoHidePinnedVisible)
```

That gives you exactly the desired result:

- bar visible → Niri tiles stop below/above it;
- bar hidden → Niri tiles reclaim the space;
- bar revealed → Niri gives the space back automatically.

This should work much better than trying to issue Niri window-resize commands, since the bar’s exclusive zone is the mechanism designed for this purpose. Noctalia’s documentation confirms that `reserve_space` controls whether the compositor pushes windows away, while `margin_opposite_edge` can add extra reserved space if the bar’s thickness is undercounted. Exactly. The **actual window resizing should be handled by Niri**, not Noctalia.

The division of responsibility is:

- **Noctalia:** decides whether its bar is visible and reports the appropriate Wayland layer-shell geometry/exclusive zone.
- **Niri:** receives that change, recomputes the usable area for the monitor, and positions tiled windows within the new area.
- **Applications:** receive normal Wayland configure events and resize their surfaces accordingly.

So the main challenge is not “how do we resize every window?” It is:

> How do we make Noctalia change its exclusive zone from the bar height to zero when auto-hidden, and back again when revealed?

Niri already supports layer-shell surfaces and layout space reserved by them; its own documentation describes layer-shell surfaces as compositor-managed surfaces, while Niri’s core behavior is to position windows according to the available monitor layout. [1,2]

The flow should be:

```text
Noctalia bar visible
    ↓
exclusive zone = 32 px
    ↓
Niri usable area loses 32 px
    ↓
tiled windows receive new sizes

Noctalia bar hidden
    ↓
exclusive zone = 0 px
    ↓
Niri usable area gains 32 px
    ↓
tiled windows expand
```

That means a Noctalia-only implementation may be sufficient if Noctalia already updates the layer-shell exclusive zone during auto-hide. You would only need to change Noctalia’s visibility logic so it performs:

```text
visible → exclusive zone = bar height
hidden  → exclusive zone = 0
```

You probably **do not need to modify Niri** unless one of these is true:

- Niri only reads the exclusive zone once when the bar is created.
- Niri has a bug handling dynamic exclusive-zone changes.
- The Noctalia bar hides visually but leaves its layer-shell surface and reserved area unchanged.
- You want special behavior for floating windows, fullscreen windows, or per-workspace rules.

One Niri-specific wrinkle is that Niri is scrollable tiling: opening a new window normally does not resize existing windows. That does not prevent a monitor usable-area change from affecting them, but it means the result may differ from a traditional grid tiler. Niri may adjust the vertical dimensions of tiled columns while preserving its horizontal scrolling and column structure. [2]

So I’d test this in layers:

1. Make a tiny test layer-shell bar whose exclusive zone changes between `32` and `0`.
2. Run it under Niri and confirm tiled windows follow the change.
3. If they do, patch Noctalia only.
4. If they do not, investigate Niri’s dynamic layer-shell/exclusive-zone handling.

In short: **Noctalia owns the trigger and reserved-space advertisement; Niri owns the resulting window relayout.** The likely bug or missing feature is entirely in the handoff between those two, not in manually resizing application windows.

GPT-5.6 Luna:
Yes—it’s feasible and should be safe for system stability if implemented through Wayland’s normal layer-shell exclusive-zone mechanism.

The safe architecture is:

```text
Noctalia changes exclusive zone
        ↓
Niri recalculates usable monitor area
        ↓
Niri sends normal configure events
        ↓
applications resize themselves
```

That avoids directly manipulating application windows, sending synthetic input, or repeatedly forcing resize commands. A failure would most likely be limited to visual/layout problems—such as a bar overlapping windows, a one-frame jump, or space not being reclaimed—not a system crash.

The main risks are:

- **Update feedback loops:** bar visibility changes the layout, which somehow changes bar visibility again.
- **State desynchronization:** Noctalia thinks the bar is hidden while Niri still reserves its space, or vice versa.
- **Rapid toggling:** animations or pointer-triggered auto-hide cause repeated exclusive-zone changes.
- **Floating-window edge cases:** tiled windows may respond correctly while floating windows remain where they were.
- **Fullscreen behavior:** fullscreen applications may intentionally ignore or override panel reservation.
- **Malformed geometry:** a bug that reports a negative, excessively large, or rapidly changing exclusive zone.

These are manageable with a few safeguards:

```text
exclusive zone ∈ {0, bar_height}
```

Use only two stable states rather than continuously changing values during the animation. Update the zone once when hiding begins and once when showing completes, or vice versa. Also debounce repeated visibility changes and ensure the update is idempotent—calling “bar is hidden” twice should still produce the same result.

A particularly robust design would be:

```qml
function updateExclusiveZone() {
    const zone = autoHideEnabled && !barVisible
        ? 0
        : barThickness

    if (zone !== currentExclusiveZone) {
        currentExclusiveZone = zone
        syncBarExclusiveZone(zone)
    }
}
```

I would avoid the less-safe approach of repeatedly running Niri commands to resize every window. That could fight Niri’s own layout engine, produce race conditions, and behave badly when windows open or close.

The sensible development process is:

1. Test with a fixed-height bar and no animation.
2. Toggle between exclusive zones of `bar_height` and `0`.
3. Test tiled, floating, fullscreen, and multiple-monitor layouts.
4. Add auto-hide and animation only after the basic behavior works.
5. Keep a configuration switch so the feature can be disabled instantly.
6. If possible, test in a separate user configuration or with a simple rollback command.

So the short answer is: **yes, feasible and low-risk when implemented as dynamic exclusive-zone updates; less safe if implemented as external scripts that manually resize windows.**
